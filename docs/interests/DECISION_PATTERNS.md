# Decision Patterns — 재사용 가능한 결정 축 카탈로그

> 대화에서 반복 등장한 결정 축. 사용자가 각 축에서 어떤 옵션을 선호하는지 · 왜 그렇게 결정하는지 정리. 새 프로젝트에서 동일 축 마주쳤을 때 참고.

## 사용법

- **일반 축** (프로젝트 무관): 사용자 성향이 안정적이라 대부분 같은 선택
- **프로젝트 특유 축**: 프로젝트마다 재확정 필요 (특히 자본/투자기간)
- 각 축에 **관찰된 결정 예시** 명시 — 실제 어떤 상황에서 어떻게 선택했는지

---

## 축 A. 자본 우선순위 — 자본 보존 vs 알파 창출

**옵션 스펙트럼**:
- A1: 자본 보존 최우선 (원금 잃지 않는 게 목표)
- A2: 균형
- A3: 알파 창출 최우선 (Sharpe 극대화, drawdown 감내 큼)

**사용자 선택 패턴**: **A1 (자본 보존)**

**근거** (사용자 표명):
- 초기 소액 (10-20만원) 으로 승산 검증 목적
- Real 진입 전 paper 3개월 관측
- "밤에 잠들 수 있는가" 가 시스템 성공 지표

**파생 결정**:
- 하드 손절 tight (-7% 이하)
- Daily loss limit 존재 (-3% 이상 lockout)
- 검증 게이트 통과 전 real 진입 절대 X

## 축 B. 투자 기간 — 단타 vs 중장기

**옵션 스펙트럼**:
- B1: 단타 (1-3일)
- B2: 스윙 (1-4주)
- B3: 중장기 (분기~연)

**사용자 선택 패턴**: **B1 (단타)** — alpha 프로젝트

**근거** (사용자 표명):
- 단타로 하는 것을 목표 (사용자 명시)

**파생 결정**:
- max_holding_days = 3
- Overnight 리스크 방어 (당일 청산)
- 리밸런싱 스킵 (매일 clear = 자동 리밸런스)

**주의**: 축 A (자본 보존) 와 축 B (단타) 는 시장 통계상 상충. 사용자 해석: **"단타는 알파 검증 실험"** 으로 수용. 자본 보존은 hard stop tight 로 달성.

---

## 축 C. 시스템 신뢰도 — 자동 vs 사람 승인

**옵션 스펙트럼**:
- C1: 완전 자동 (시스템 결정 = 즉시 실행)
- C2: 알림 + 자동
- C3: 알림 후 사용자 승인
- C4: 모든 결정 사용자 승인

**사용자 선택 패턴**: **C1 (완전 자동)**

**근거** (사용자 표명):
- 완전 자동 선호
- 밤에 자면서도 시스템 돌아가야 함
- Destructive action 은 예외 (classifier 게이트 존중)

**파생 결정**:
- Hard stop 즉시 실행 (Telegram 알림은 사후)
- Time exit 15:20 자동 발주
- 사용자 게이트는 **비가역 · 운영 영향 · 삭제** 케이스만

## 축 D. 감내 손실

**옵션 스펙트럼**:
- D1: Tight (일일 -2%, drawdown -5%, 개별 -5%)
- D2: 중간 (일일 -3%, drawdown -8%, 개별 -7%) ← 사용자 결정
- D3: Wide (일일 -10%, drawdown -20%, 개별 -10%)

**사용자 선택 패턴**: **D2 (중간, Kim 추천)**

**근거** (사용자 표명):
- 초기 사용자 답변은 D3 이었으나, Kim (트레이더 페르소나) 지적 후 D2 로 수정
- 축 A (자본 보존) 와 정합성 위해 조정

**파생 결정**:
- Hard stop 3-layer 파라미터 그대로
- 실 자본 증액 시 재조정 필요 (open question)

## 축 E. 감사 vs 속도

**옵션 스펙트럼**:
- E1: 감사 최우선 (event sourcing 수준)
- E2: 균형
- E3: 속도 최우선 (log 30일 aggregate)

**사용자 선택 패턴**: **E1 (감사 최우선)**

**근거** (사용자 표명):
- 감사 최우선 명시
- Commit body 상세 · PR review 흔적 · Snapshot JSONB 저장 등에 일관됨

**파생 결정**:
- `broker_orders.trigger_snapshot` JSONB 저장
- 마이그레이션 (예: DB rename, drop) 은 view 로 6개월 backward compat
- 모든 스키마 변경 시 orphan 사전 검사 리포트
- 회고록 상세 (1년 뒤 재현 가능 수준)

## 축 F. UX 대상

**옵션 스펙트럼**:
- F1: 본인 (전문가, 정보 밀도 최대)
- F2: 본인 + 지인 (친숙 사용자)
- F3: 미래 대중 (Toss 스타일, 심리 방어)

**사용자 선택 패턴**: **F1 (본인 전문)**

**근거** (사용자 표명):
- 본인 전문
- Chart / metric 위주 UI 선호

## 축 G. 기존 유지 vs 재작성

**옵션 스펙트럼**:
- G1: 기존 최대한 유지
- G2: 부분 재작성 (필요 부분만)
- G3: 완전 재작성 (clean slate)

**사용자 선택 패턴**: **G1 (기존 유지)** 강함

**관찰된 예시**:
- ETF / KONEX 등록 결정 (기존 스키마 그대로 유지, sync 로직만 추가)
- Sell strategy 4대 기능 (기존 LLM predictor 그대로 두고 안전망만 추가)
- Repo carve-out 시 코드는 그대로 두고 운영 식별자만 격리
- 옛 PR (#141, #192, #198) 은 재작성 안 하고 그냥 close (필요한 것만 fresh PR)

**Anti-pattern 지적**:
- **"컬럼 여러 개 추가"** 를 제안했을 때: "기존에 사용하고 있는 것에 추가만 하면 되는건데 뭐가 컬럼 추가가 필요한지 이해가 안가"
- **"collector 상시 로직"** 을 제안했을 때: "한 번만 필요하면 임시 스크립트만 쓰는 게 맞는 것 같은데"

**교훈**: 새 기능 제안 시 "이걸 안 만들고 기존 걸로 해결할 방법 있나?" 먼저 자문.

## 축 H. 완결 vs 확장 — YAGNI

**옵션 스펙트럼**:
- H1: 지금 필요한 것만 (YAGNI 강함)
- H2: 확장 가능한 뼈대까지
- H3: 미래 요구까지 미리 대응

**사용자 선택 패턴**: **H1 (YAGNI)**

**관찰된 예시**:
- ESB / Kafka 도입 제안 시: 지금 워크로드로는 불필요 판정
- Sell Strategy 4대 기능 중 Phase D (리밸런싱) 스킵 결정
- Trailing stop 로직 별도 세션으로 분리
- 초기 부트스트랩 script 는 repo 에 남기지도 말고 (남기면 헷갈림) 한 번 실행하고 끝

**교훈**: "미래에 필요할 수도 있어" 라는 이유로 코드 추가 X.

## 축 I. 자동화 스크립트 vs 상시 로직

**옵션 스펙트럼**:
- I1: 임시 script 1회 실행
- I2: 상시 로직 (스케줄러/collector)
- I3: 이벤트 기반 (반응적)

**사용자 선택 패턴**: 상황 따라 다르지만 **I1 을 자주 선택** (YAGNI 관점)

**관찰된 예시**:
- ETF/KONEX sync gap 해소: 임시 SQL 로 한 번 실행 (I1)
- 미래 IPO 자동 등록은 별개 결정으로 분리 (필요할 때 재검토)

**의사결정 규칙**:
- 지금 필요한 delta 가 한 번? → I1
- 지속적으로 발생? → I2 검토
- 진짜 event-driven 필요? → I3

## 축 J. 저장소 분리 정책

**옵션 스펙트럼**:
- J1: 단일 repo (mono)
- J2: 논리적 분리 (public + private)
- J3: 서비스별 완전 분리 (microservice)

**사용자 선택 패턴**: **J2 (논리적 분리)**

**관찰된 예시**:
- `alpha-financial-pipeline` (public, 메인 코드)
- `agents-investing-ops` (private, 운영 식별자 IP/OCID)
- `agents-investing-infisical` (private, Infisical 인프라)

**근거**:
- 코드는 이력서/포트폴리오 가치 (public)
- 네트워크 정체성 (IP/OCID) 은 attack surface 차단 (private)
- Infisical 은 시크릿 저장소 자체라 별도 (private)

## 결정 축의 재활용 규칙

**새 프로젝트 시작 시**:
1. `projects/새프로젝트.md` 파일 생성
2. **필수 확정 축**: A (자본), B (기간), C (자동화) — 프로젝트별 다름
3. **일반 재활용 축**: E (감사), F (UX), G (기존 유지), H (YAGNI) — 대체로 동일
4. 새 축이 등장하면 이 카탈로그에 추가

**갱신 시점**:
- 사용자가 명시적으로 "이제 다른 방향" 이라고 표명 시
- 프로젝트 단계 변경 시 (예: paper → real 전환 후 감내 손실 재조정)
